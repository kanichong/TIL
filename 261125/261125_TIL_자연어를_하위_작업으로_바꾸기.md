지시 해석 · 로봇이 정해야 할 것
“A에서 상자를 가져와 B에 놓고 충전해.”
로봇 앞에 상자가 두 개라면 무엇을 집어야 할까? 충전기에 도착만 하면 지시를 끝낸 걸까?
지시를 대상 · 도착 장소 · 완료 조건으로 나누어 적습니다.
이 강의에서는 빨간 상자를 옮기고, 충전이 시작되면 끝나는 것으로 약속합니다.

완료 조건 · ‘충전해’를 검사할 수 있는 조건으로
지시의 일부  -  완료 조건  -  확인할 때
B에 놓아  -  선택한 상자가 B에 있고 손은 비어 있음  -  놓은 직후
충전해  -  충전기 D에 연결되고 충전 중 신호가 켜짐  -  도킹 후
놓고 충전해  -  상자를 놓은 뒤에 충전을 시작함  -  두 사건의 시각 비교
최종 상태만 검사하면 ‘먼저 충전하고 나중에 상자를 옮긴’ 기록도 통과합니다. ‘놓고’에는 순서 조건이 들어 있습니다.

대상 선택 · “A에 있는 빨간 상자”는 어느 쪽일까?
작업대 A 위에 빨간 상자 두 개: box_01 (입구 쪽) · box_02 (창가 쪽)
색만으로 후보가 하나로 좁혀지지 않음 → 로봇이 되묻기: “둘 다 빨간 상자예요. 입구 쪽과 창가 쪽 중 어느 것을 옮길까요?”
사용자가 ‘창가 쪽’을 고르면 그 답을 현재 배치와 대조해 box_02를 선택합니다.

작업 명세 · 모델과 실행기가 주고받는 형식
```json
{
  "id": "t2",
  "op": "pick",
  "object_id": "box_02",
  "after": ["t1"]
}
```
필드  -  실행 전에 검사할 것
id  -  t2는 이 계획에서 한 번만 쓰임
op  -  pick이 허용 목록에 있어야 함
object_id  -  box_02가 관측 목록에 있어야 함
after  -  t1이 실제로 등록한 선행 작업이어야 함
질문: t1을 정의하지 않은 채 이 명세를 보내면? → 선행 ID 존재 검사에서 걸림 (미등록 노드)

실행 확인 · 집기 명령을 보낸 뒤
12:00:00 집기 직전  →  12:00:01 명령 전송  →  12:00:02 결과 관측
집기 직전: box_02가 팔의 작업 범위에 있고 손은 비어 있음
명령 전송: pick(box_02)를 보냄 · 이 시점의 파지 상태는 아직 미확인
결과 관측: 그리퍼는 닫혔지만 상자는 작업대에 그대로 → B로 출발하면 안 됨
예상한 효과는 holding(box_02)이지만, 다음 작업의 사전조건에는 실제로 확인한 결과를 넘깁니다.

관측 상태 · B의 빈자리를 보지 못했다면
관측  -  상태 기록  -  놓기 전에 할 일
선반이 비어 있는 것이 보임  -  free(B) = true  -  관측이 여전히 유효한지 확인
다른 물체가 차지함  -  free(B) = false  -  공간이 생길 때까지 대기하거나 목적지 문의
카메라가 가려짐  -  free(B) = unknown  -  시야를 확보하고 다시 관측
관측이 끊겼을 때 false를 임의로 넣으면 ‘가려졌다’는 정보가 사라집니다. 상태는 true / false / unknown 세 값으로 다룹니다.

작업 그래프 · ‘놓기’로 모이는 두 갈래
상자를 B까지 가져가는 경로와 B가 비었는지 확인하는 경로를 따로 그립니다.

A 이동  →  집기  →  B 이동  →  놓기  →  충전기로
B 공간 조회  →  놓기 (두 선행 작업 모두 완료돼야 시작)

간선 하나를 가려 보면: ‘B 이동 → 놓기’가 없으면 로봇은 B에 도착하기 전에 상자를 내려놓을 수 있습니다.

작업 그래프 · 노드가 기다리는 대상을 코드로
작업 ID  -  의미  -  선행 ID
A / check  -  A로 이동 / B의 공간 조회  -  각각 없음
pick / B  -  상자 집기 / B로 이동  -  각각 A / pick
place  -  상자 놓기  -  B와 check 모두
D / charge  -  충전기로 이동 / 충전 시작  -  각각 place / D
after에는 바로 앞의 선행 작업만 적어도 됩니다. A가 pick을 거쳐 B에 이어진다는 관계는 그래프에 이미 들어 있습니다.

위상 정렬 · 한 번 손으로 계산하기
위상 정렬: 선행 작업 수(진입 차수)가 0인 노드부터 꺼내고, 꺼낸 노드를 기다리던 노드의 수를 1씩 줄이는 반복
방금 완료한 작업  -  남은 선행 작업 수 변화  -  다음에 가능한 작업
아직 없음  -  A = 0, check = 0, place = 2  -  A, check
A와 check  -  pick 1→0, place 2→1  -  pick
pick  -  B 1→0  -  B
B  -  place 1→0  -  place
place가 2→1로 바뀐 순간: 공간 조회는 끝났지만 상자는 아직 B에 도착하지 않았습니다.

순환 · A가 자기 자신의 완료를 기다리게 된 이유
정상 계획에 ‘A로 이동하려면 먼저 상자를 놓아야 한다’는 간선 place → A를 잘못 추가한 경우

A 이동  →  집기  →  B 이동  →  놓기  →  (다시) A 이동

어느 노드도 선행 작업 수가 0이 되지 않아 정렬이 멈춥니다.
고칠 때는 A의 선행 목록에서 place를 지웁니다. pick이나 B를 지우면 운반에 필요한 조건까지 사라집니다.

자원 · 같이 시작할 수 있는 작업과 같은 장비를 쓰는 작업
작업 간 선후 관계와 장비 사용 시간은 따로 확인합니다.
장비  -  사용하는 작업
차체  -  A로 이동, B로 이동
그리퍼  -  상자 집기
고정 카메라  -  B 공간 조회
고정 카메라의 조회는 차체 이동과 겹칠 수 있지만, A 이동과 B 이동은 차체 하나를 쓰므로 같은 시간에 실행할 수 없습니다.
그래프상 동시에 가능해도 장비가 겹치면 자원 충돌입니다.

상태 전이 · 행동 하나가 상태의 어느 칸을 바꿀까?
직전 행동  -  로봇 위치 / 상자 위치 / 손 상태  -  다음 행동
시작  -  A / A / 비어 있음  -  pick
pick 성공  -  A / 손 / box_02를 쥠  -  move(B)
move(B) 성공  -  B / 손 / box_02를 쥠  -  place
place 성공  -  B / B / 비어 있음  -  운반 목표 확인
세 번째 행에서 로봇은 B에 있지만 상자는 아직 손에 있습니다. 도착과 내려놓기는 다른 사건입니다.

계획 방법 비교 · 손에 다른 상자가 들려 있다면
방법  -  접근  -  손이 찬 초기 상태에서
상태 공간 탐색  -  현재 가능한 행동부터 찾음  -  pick은 제외 → 지정된 임시 보관대에 기존 상자를 놓을 수 있는지 검사
작업 분해  -  ‘접근 → 집기 → 이송 → 놓기’ 틀을 펼침  -  집기의 사전조건이 막힘 → 기존 상자를 보관하는 하위 작업을 넣을 수 있는지 확인
토론: 임시로 내려놓을 자리가 없다면 두 방법은 어느 단계에서 멈출까?

재계획 · 집기 실패 로그에서 재시작 지점 찾기
관측 1 위치: 로봇은 A에 도착, 최신 위치 추정도 A
관측 2 파지: 닫기 명령 뒤 상자가 탁자에 남음 · 물체 중심이 이전보다 옆으로 밀림
다음 시도: 상자의 현재 자세를 추정하고 집기 목표를 다시 계산 → 파지가 확인되면 B로 이동
A 도착은 여전히 유효합니다. 바뀐 사실(상자 자세 · 파지 상태)부터 고치며, 처음부터 다시 계획하지 않습니다.

목적지 변경 · B가 막혔는데 옆 선반은 비어 있다
상황: 로봇은 box_02를 쥐고 있고 B에는 다른 물체가 있음. 옆 선반 C는 비어 있지만 사용자가 정한 목적지는 B
“옆 선반에 내려놓으면 운반을 끝낸 걸까?” → 아니다. 목적지는 사용자가 정한 것
처리 순서: B를 다시 관측 → 점유가 확인되면 대기하거나 “C에 놓아도 될까요?”라고 질문 → 답이 오면 남은 놓기 · 충전 작업 갱신

실습 ① · 상자 운반 계획을 종이에 그리기
조건: A에 빨간 상자 두 개, 사용자는 창가 쪽(box_02) 선택, B의 고정 카메라는 차체와 따로 사용 가능
과제  -  답
첫 두 작업  -  동시에 시작할 수 있는 두 노드 (A 이동, B 공간 조회)
합류점  -  놓기 노드로 들어가는 두 화살표 (B 이동 → 놓기, B 공간 조회 → 놓기)
종료 조건  -  B에 놓기와 충전 시작을 확인할 관측값

실습 ② · 종이에 그린 순서와 Python 출력 비교
Python 3.9 이상 · graphlib
```python
from graphlib import TopologicalSorter

plan = {'A': (), 'check': (), 'pick': ('A',),
        'B': ('pick',), 'place': ('B', 'check')}
order = tuple(TopologicalSorter(plan).static_order())
print(order)   # ('A', 'check', 'pick', 'B', 'place')

plan2 = dict(plan, D=('place',), charge=('D',))
print(tuple(TopologicalSorter(plan2).static_order()))
# ('A', 'check', 'pick', 'B', 'place', 'D', 'charge')
```
check가 A보다 먼저 와도 유효합니다. place의 왼쪽에 B와 check가 모두 있는지 봅니다.

실습 ③ · 한 줄을 바꿔 순환 재현하기
```python
from graphlib import CycleError

broken = dict(plan, A=('place',))
try:
    tuple(TopologicalSorter(broken).static_order())
except CycleError as err:
    print(err.args[1])   # ['A', 'pick', 'B', 'place', 'A']
```
처음과 끝이 같은 노드입니다. A의 선행 목록을 빈 튜플로 되돌린 뒤 정상 입력의 결과와 비교합니다.

실습 ④ · 어느 상자인지 되묻는 답 만들기
사용자: “A에 있는 빨간 상자를 옮겨 줘.”
로봇: “입구 쪽과 창가 쪽에 하나씩 있어요. 어느 쪽인가요?”
사용자: “창가 쪽.” → 현재 관측과 대조해 box_02 선택
A 대신 지도에 없는 Z를 넣으면? → 물체를 고르는 질문과 위치를 확인하는 질문을 각각 한 줄로 작성

동료 검토 · 짝의 계획에서 오류 세 개 찾기
일부러 넣은 오류  -  검사  -  예상 진단
pick이 존재하지 않는 t9를 기다림  -  모든 선행 ID가 명세에 있는가?  -  미등록 노드
손이 빈 상태에서 place를 제안  -  현재 상태가 사전조건을 만족하는가?  -  파지 조건 불충족
A와 D로 동시에 이동  -  같은 시간에 차체를 몇 작업이 쓰는가?  -  자원 충돌
TopologicalSorter는 선행 목록에만 있는 ID도 노드로 받아들입니다. t9 오타는 별도 검사로 잡아야 합니다.
```python
typo = dict(plan, pick=('t9',))
print(tuple(TopologicalSorter(typo).static_order()))
# ('A', 'check', 't9', 'pick', 'B', 'place')  ← 오류 없이 통과

known = set(plan)
missing = {p for deps in typo.values() for p in deps} - known
print(missing)   # {'t9'}
```

마무리 · 어디서 멈추고, 무엇을 고칠까?
장면  -  멈추는 이유  -  다시 시작하는 조건
A · 대상 선택 (같은 상자 두 개, 색만 지정)  -  같은 설명에 두 후보가 일치  -  사용자 답과 현재 관측으로 한 ID 확정
B · 계획 구조 (놓기 전엔 A에 못 가고, A에 가야 집음)  -  선행 작업을 따라가면 처음 노드로 복귀  -  잘못된 간선 수정 후 전체 정렬 성공
C · 실행 결과 (집기는 끝났는데 상자가 탁자 위에)  -  기대했던 파지 상태와 관측이 다름  -  물체 재관측 후 집기 성공 확인
