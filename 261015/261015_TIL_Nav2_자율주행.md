

SLAM과 Navigation
SLAM은 지도와 로봇의 위치·방향을 함께 추정한다.
Navigation은 현재 위치에서 목표까지 갈 경로와 속도 명령을 만든다.
저장 지도 주행에서는 AMCL이 위치를 추정하고 Nav2가 주행을 수행한다.

Nav2 스택구조
BT Navigator: 계획·제어·복구 작업 조율
Planner: 경로 / Controller: 속도 명령
Costmap: 충돌 위험과 통과 비용

위치·센서  —  TF / odom / scan  —  시간·좌표계가 맞아야 지도와 센서를 함께 해석할 수 있다.
경로  —  nav_msgs/Path  —  지나갈 위치·방향의 열. 속도·시간이 반드시 포함되지는 않는다.
속도 명령  —  Twist / TwistStamped  —  Waffle Lyrical 예제는 TwistStamped 연결을 확인한다.

경로와 궤적
경로(Path)는 공간에서 어디를 지나갈지를 나타낸다.
궤적(Trajectory)은 시간에 따른 상태·속도까지 포함한다.
Planner가 경로를 만들고 Controller가 로봇 운동 제약과 장애물을 고려해 추종한다.

TF구조
map → odom: 저장 지도 주행에서는 AMCL이 전역 위치를 보정한다.
odom → base_footprint: Gazebo 또는 오도메트리가 연속 이동을 발행한다.
base_footprint → 센서: URDF에 정의된 고정 변환을 확인한다.

주행 모드 전환
저장 지도 주행 전 Cartographer·cuVSLAM의 map → odom 발행을 중지한다.
AMCL과 SLAM이 같은 TF를 동시에 발행하면 위치가 흔들릴 수 있다.
Gazebo·Nav2·RViz는 /clock과 use_sim_time 설정을 맞춘다.

AMCL 정의
AMCL: Adaptive Monte Carlo Localization. 적응형 몬테카를로 위치 추정.
알려진 2D 지도에서 로봇의 위치·방향 (x, y, θ)을 추정한다.
여러 위치 가설을 입자로 표현하며 불확실성에 따라 입자 수를 조절한다.

SLAM  — 지도 + 위치 추정  —  새 환경의 지도를 만들면서 위치를 찾는다.
AMCL  —  지도 안의 위치 추정  —  저장된 지도가 필요하며 새로운 지도를 만드는 도구가 아니다.
Odometry  —  상대 이동량  —  연속적인 이동 추정에 유용하지만 시간이 지나면 오차가 쌓인다.

입자 필터 과정
예측: 오도메트리 이동량과 잡음을 반영해 입자를 움직인다.
갱신: 각 입자의 위치에서 예상되는 지도와 실제 LiDAR 관측을 비교한다.
재표본화: 관측과 잘 맞는 가설이 다음 입자 집합에 더 많이 남는다.

초기 위치와 불확실성
RViz의 2D Pose Estimate로 현재 위치와 방향의 초기 가설을 준다.
입자가 넓게 퍼지면 위치 불확실성이 크다는 뜻이다. 한 점처럼 보인다고 정답이 보장되지는 않는다.
반복 복도·잘못된 지도·틀린 센서 TF에서는 다른 위치로 수렴할 수 있다.

AMCL 좌표계
global_frame_id  —  map  —  저장 지도 좌표계. map → odom 보정에 사용한다.
odom_frame_id  —  odom  —  연속 이동을 표현하는 오도메트리 좌표계.
base_frame_id  —  base_footprint  —  Waffle 예제 기준. 실제 TF 이름과 일치시킨다.

AMCL 입력 설정
scan_topic  —  scan / /scan  —  실제 LaserScan 토픽, 프레임과 시간을 확인한다.
robot_model_type  —  DifferentialMotionModel  —  Waffle 차동 구동 모델. Omni 모델을 쓰지 않는다.
tf_broadcast  —  true —   AMCL이 map → odom 발행. 다른 발행자와 중복 금지.

AMCL 입자 수
min_particles  —  500  —  기준 YAML 값. 최소 가설 수와 계산량에 영향을 준다.
max_particles  —  2000  —  불확실할 때 사용할 상한. 늘려도 잘못된 지도는 해결되지 않는다.
pf_err / pf_z  —  0.05 / 0.99  —  적응 입자 수의 오차·신뢰 설정. 관측 품질부터 점검한다.

AMCL 이동 잡음
alpha1  -— 회전 → 회전 잡음  —  회전량 때문에 발생하는 회전 추정 불확실성.
alpha2  —  이동 → 회전 잡음  —  병진 이동량 때문에 발생하는 회전 불확실성.
alpha3  —  이동 → 이동 잡음  —  병진 이동량 때문에 발생하는 병진 불확실성.
alpha4  —  회전 → 이동 잡음  —  회전 때문에 발생하는 병진 추정 불확실성.
alpha5  —  Omni 모델 추가 항  —  옴니 구동의 병진 잡음 계수. Waffle 차동 모델에는 적용되지 않는다.
선택 근거  —  실제 odom 오차  —  직진·회전 실험에서의 오차 경향을 관측한 뒤 조정한다.

AMCL 레이저 모델
laser_model_type  —  likelihood_field  —  레이저 끝점과 지도 장애물 간 거리로 관측 적합성을 평가한다.
sigma_hit  —  0.2 m  —  끝점 거리 오차 모델 폭. 너무 좁으면 작은 불일치에도 민감해진다.
z_hit / z_rand  —  0.5 / 0.5  —  정상 관측 / 무작위 관측 혼합 가중치. 활성 모델 항을 확인한다.

AMCL 갱신 주기
update_min_d  —  0.25 m  —  이만큼 이동한 뒤 필터 갱신. 작게 하면 갱신·계산 부담 증가.
update_min_a  —  0.2 rad  —  각도 기준. 직선 거리와 별개로 회전 중 갱신을 결정한다.
max_beams  —  60  —  평가에 사용할 광선 수. 입력·계산 시간과 함께 선택한다.

AMCL 시간과 재표본화
resample_interval  — 1 —  필터 갱신 몇 회마다 재표본화할지 결정한다.
transform_tolerance  —  1.0 s  —  발행 TF의 유효 시간 여유. 통신 지연 자체를 고치는 값은 아니다.
검증 항목  —  scan 정렬 / pose  —  지도 벽과 레이저가 맞는지, 회전 후 위치가 튀는지 관찰한다.

AMCL 진단 예제
증상: 로봇을 돌릴 때 스캔이 지도 벽에서 크게 벗어난다.
먼저 센서 TF·시각·odom 방향·지도 해상도를 확인한다.
입자 수를 올리기 전에 초기 위치와 모델 입력이 올바른지 검증한다.

전역 경로 계획
Dijkstra · A* · Smac · Theta
탐색 비용과 로봇 운동 제약

지도와 Costmap
점유지도: 공간의 점유 상태
Costmap: 지도상에서 주행 위험을 비용으로 표현
같은 거리라도 벽 근처 경로의 비용이 더 높을 수 있다.

**Dijkstra**
출발점부터 누적 비용 g가 가장 작은 후보를 순서대로 확장한다.
간선 비용이 음수가 아닌 그래프에서 최소 비용 경로를 찾는다.
목표 방향의 휴리스틱 없이 탐색하므로 넓은 영역을 살필 수 있다.

A*
누적 비용 g와 목표까지의 예상 비용 h를 합한 f = g + h로 후보를 선택한다.
h가 목표 방향 탐색을 도와 불필요한 확장을 줄일 수 있다.
최적성은 휴리스틱 조건과 구현에 달려 있다. 항상 더 짧거나 빠른 것은 아니다.

Dijkstra와 A* 선택
우선순위  —  g / g + h  —  Dijkstra는 누적 비용, A*는 목표 추정 비용까지 사용한다.
비교 조건  —  같은 지도·같은 비용  —  알고리즘 이름만으로 경로 길이·안전성을 단정하지 않는다.
선택 실험  —  시간·성공률·경로  —  좁은 미로와 넓은 공간에서 각각 반복 비교한다.

NavFn 알고리즘 선택
```
planner_server:
  ros__parameters:
    planner_plugins: ["GridBased"]
    GridBased:
      plugin: "nav2_navfn_planner::NavfnPlanner"
      use_astar: false
      allow_unknown: false
      tolerance: 0.5
```
use_astar: false → Dijkstra / true → A*
미탐색 영역을 통과하지 않도록 allow_unknown: false

NavFn 파라미터
use_astar  —  false / true  —  동일 플러그인에서 탐색 방식을 바꾼다.
allow_unknown  —  bool  —  미탐색 셀 통과 허용. Unknown을 안전한 공간으로 단정하지 않는다.
tolerance  —  m  —  정확한 목표가 막혔을 때 근처 경로 끝점 탐색 범위. 도착 허용 오차와 다르다.

Planner 선택지
NavFn  —  Dijkstra / A*  —  격자 기반의 일반적인 시작점. Waffle 비교 실습에 적합.
Smac 2D  —  비용 인식 A*  —  2D 격자 탐색. 차동·옴니 등 제자리 방향 전환 가능한 로봇.
Theta*  —  Any-angle 탐색  —  가시선으로 격자 방향 제약을 줄인다. 회전 가능성은 별도 점검.
Smac Hybrid-A*  —  SE(2) 탐색  —  위치와 방향을 함께 고려. Dubins / Reeds–Shepp 운동 모델.
Smac State Lattice  —  운동 프리미티브  —  사전 정의된 가능한 움직임으로 연결. 로봇 모델과 격자를 맞춘다.
Waffle 기준  —  2D 계획부터 비교  —  차동 구동·제자리 회전이 가능하다. 차량용 제약을 무조건 추가하지 않는다.

Planner 클래스명
Smac 2D  —  nav2_smac_planner::  —  SmacPlanner2D
Hybrid-A* / Lattice  —  nav2_smac_planner::  —  SmacPlannerHybrid / SmacPlannerLattice
Theta*  —  nav2_theta_star_planner::  —  ThetaStarPlanner

Smac 파라미터 선택
tolerance / allow_unknown  —  m / bool  —  목표 부근 허용 범위와 Unknown 통과 정책.
cost_travel_multiplier  —  Smac 2D 비용 계수  —  높은 Costmap 비용의 회피 정도. 경로·시간을 함께 비교한다.
max_planning_time  —  s  —  계획 시간 예산. 실시간 요구와 지도의 복잡도를 함께 고려한다.

Hybrid-A* 운동 제약
minimum_turning_radius  —  m  —  가능한 최소 회전 반경. 실제 조향·주행 모델에 근거한다.
angle_quantization_bins  —  방향 구간 수  —  방향 해상도를 높이면 탐색 상태·계산량이 늘 수 있다.
motion_model_for_search  —  DUBIN / REEDS_SHEPP  —  전진 전용 / 전후진 허용 모델. 실제 구동 가능성과 맞춘다.

확장 알고리즘: RRT와 PR
RRT는 공간을 샘플링해 트리를 확장하고, PRM은 샘플 간 연결 지도를 만든다.
고차원·복잡한 운동 계획에서 활용한다. 일반 RRT의 최적 경로는 보장되지 않는다.
Nav2 기본 Planner 선택 목록과 구분한다. 사용하려면 별도 통합·플러그인 구현을 확인한다.

Planner 비교 실습
동일 지도·동일 출발·동일 목표로 NavFn Dijkstra와 A*를 비교한다.
그다음 Smac 2D를 비교하고, 경로 길이·벽과의 간격·계획 시간을 기록한다.
경로가 있어도 로봇이 추종하지 못하면 Controller·Footprint·속도 제한을 확인한다.

지역 제어
DWB · MPPI · RPP · Graceful Controller
속도 명령 · 충돌 회피 · 경로 추종

Controller 역할
현재 위치·속도, 경로, 주변 Costmap을 받아 다음 속도 명령을 계산한다.
Waffle은 선속도 vx와 각속도 wz를 사용한다. vy는 0이다.
새 장애물을 피하려면 관측 갱신과 필요 시 전역 재계획도 함께 작동해야 한다.

DWB 원리
속도 후보를 샘플링하고 Trajectory Generator로 짧은 궤적을 예측한다.
Critic이 장애물·경로 거리·목표 방향 등을 평가한다.
유효한 후보 중 가중 비용이 작은 궤적의 속도 명령을 선택한다.

DWB 궤적 생성기
StandardTrajectoryGenerator  —  Trajectory Rollout  —  속도 후보를 전개하는 기본 방식. DWB를 DWA와 완전히 동일하게 보지 않는다.
LimitedAccelGenerator  —  DWA 계열  —  가속 한계를 반영해 도달 가능한 속도 범위를 다루는 생성기.
trajectory_generator_name  —  생성기 플러그인  —  후보 생성 방식과 Critic 평가를 구분한다. 설치 클래스와 파라미터를 확인한다.

DWB 속도와 예측
max_vel_x / max_vel_theta  —  m/s / rad/s  —  최대 직진·회전 속도. 구동계와 최종 출력 제한을 맞춘다.
acc_lim_x / acc_lim_theta  —  m/s² / rad/s²  —  가속 한계. 감속 한계 decel_lim_*는 부호와 구현을 확인한다.
sim_time  —  s  —  궤적 예측 길이. 너무 짧으면 앞 장애물을 늦게 고려할 수 있다.

DWB 샘플링
vx_samples / vtheta_samples  —  후보 수  —  늘리면 선택이 촘촘해지지만 후보 평가량도 증가한다.
vy_samples / max_vel_y  —  횡방향 후보 / m/s  —  Waffle은 max_vel_y=0. 횡이동 후보를 만들지 않는다.
linear_granularity  —  m  —  궤적 충돌·비용 평가 간격. 너무 거칠면 평가가 부정확할 수 있다.

DWB Critic
BaseObstacle / ObstacleFootprint  —  장애물 비용  —  장애물 접근·충돌을 평가. 유효성 검사를 가중치로 대신하지 않는다.
PathDist / PathAlign  —  경로 추종  —  경로 거리와 진행 방향 정렬을 평가한다.
GoalDist / GoalAlign  —  목표 접근  —  목표 거리와 방향 정렬을 평가한다.
RotateToGoal  —  목표 부근 회전  —  목표 근처에서 방향을 맞추는 동작을 평가한다.
Oscillation  —  반복 왕복 억제  —  방향을 바꾸며 제자리에서 흔들리는 동작을 억제한다.
각 Critic의 scale  —  비용 가중치  —  항 간 우선순위를 바꾼다. 척도가 달라 숫자만 단순 비교하지 않는다.

MPPI 원리
Model Predictive Path Integral: 여러 제어 시퀀스를 샘플링하고 미래 궤적을 예측한다.
각 궤적의 비용에 따라 제어 시퀀스를 가중 갱신한다.
첫 제어만 적용한 뒤 다음 주기에 새 관측으로 다시 계산한다.

MPPI 예측 궤적
공식 데모: 경로·Costmap·예측 결과
장애물·경로·목표 비용으로 후보 평가
다음 주기마다 새 상태로 다시 예측한다.

MPPI 계산 환경
MPPI는 벡터화된 계산을 활용한다. NVIDIA GPU가 필수인 알고리즘은 아니다.
샘플 수·예측 길이·Critic 수가 계산 시간을 바꾼다.
최신 알고리즘이라는 이유보다 제어 주기를 지킬 수 있는지로 선택한다.

MPPI 예측 길이
time_steps  —  56  —  설치본 참고 예측 단계 수. 더 멀리 보려면 계산량도 점검한다.
model_dt  —  0.05 s  —  한 단계 시간. controller_frequency=20 Hz의 주기와 맞춘다.
예측 시간  —  56 × 0.05 = 2.8 s  —  시간을 늘려도 속도 제한 때문에 공간적 전망이 짧을 수 있다.

MPPI 샘플과 탐색
batch_size  —  2000  —  설치본 참고 후보 수. 늘리기 전 제어 주기 초과 여부를 확인한다.
vx_std / wz_std  —  m/s / rad/s  -—  제어 샘플의 퍼짐. 작으면 탐색이 좁고 크면 거친 후보가 늘 수 있다.
iteration_count  —  1  —  주기 내 최적화 반복 수. 단계·샘플과 함께 계산량에 영향을 준다.

MPPI 가중치와 모델
temperature  —  0.3  —  비용 차이에 대한 가중 민감도. 낮을수록 낮은 비용 후보에 집중한다.
gamma  —  0.015  —  제어 에너지 관련 정규화 계수. Critic scale과 다른 역할이다.
motion_model  —  diff_drive  —  이 설치본은 플러그인 모델 이름을 사용한다. 옛 DiffDrive 예제와 구분한다.

Lyrical MPPI 모델 설정
```
FollowPath:
  plugin: "nav2_mppi_controller::MPPIController"
  motion_model: "diff_drive"
  diff_drive:
    plugin: "mppi::DiffDriveMotionModel"
  vy_max: 0.0
  vx_max: 0.1
  vx_min: -0.1
  wz_max: 0.2
```
기존 Waffle README의 보수적인 시뮬레이션 시작값
FollowPath는 controller_server.ros__parameters 아래에 둔다.

MPPI Critic
ConstraintCritic  —  운동 제약  —  속도·가속 등의 제약 위반 비용을 평가한다.
CostCritic  —  Costmap 비용  —  장애물·고비용 구역을 평가한다. Footprint 설정도 확인한다.
GoalCritic / GoalAngleCritic  —  목표 위치 / 방향  —  목표 근처의 위치·방향 오차를 평가한다.
PathFollowCritic  —  경로 진행  —  경로를 따라 앞으로 진행하도록 유도한다.
PathAlignCritic / PathAngleCritic  —  경로 정렬 / 방향  —  경로와의 정렬 및 진행 각도를 평가한다.
PreferForwardCritic  —  전진 선호  —  후진을 덜 선호하도록 비용 부여. 후진 가능성을 삭제하는 값은 아니다.

MPPI 평가 설정
cost_weight  —  각 Critic 가중치  —  해당 비용 항의 중요도. 활성 Critic과 함께 확인한다.
threshold_to_consider  —  m 등 플러그인별  —  목표 부근 등 조건부 평가 범위. 단위·기준은 Critic마다 확인한다.
visualize  —  bool  —  예측 궤적 확인에 유용. 계산 부담이 있으면 관찰 후 끈다.

Controller 선택지
DWB  —  속도 후보 + Critic  —  후보 평가를 관찰하며 튜닝. 좁은 곳의 진동·유효 후보 수 점검.
MPPI  —  제어 시퀀스 최적화  —  미래 궤적 기반 회피. 시간 예산·Critic 균형 점검.
RPP  —  Regulated Pure Pursuit  —  Lookahead 추종과 속도 조절. 가벼운 정밀 경로 추종에 검토.
Graceful Controller  —  부드러운 경로 추종  —  매끄러운 접근·제어가 필요한 경우. 운동·장애물 제약 확인.
Rotation Shim  —  방향 정렬 래퍼  —  주 Controller 전에 방향을 맞춘다. 독립 전역 Planner가 아니다.
선택 원칙  —  로봇·경로·환경·CPU  —  특정 알고리즘이 모든 환경에서 가장 좋은 것은 아니다.

확장 선택지: DWPP
DWPP  —  Dynamic Window Pure Pursuit  —  Pure Pursuit에 속도·가속 제약을 고려하는 최신 확장 선택지.
use_dynamic_window  —  최신 Rolling 문서 항목  —  기존 RPP 설정과 지원 범위가 다르다. 설치본에 존재하는지 확인한다.
수업 적용  —  기본 비교 이후 확장  —  Lyrical 1.5.0 기본 예제에서 검증한 기능으로 취급하지 않는다.

RPP 파라미터 선택
최대 선속도  —  m/s  —  설치본 이름을 확인한다. 최신 Rolling은 max_linear_vel, 이전 이름은 desired_linear_vel.
lookahead_dist  —  m  —  추종할 앞쪽 지점. 작으면 민감, 크면 코너를 크게 돌 수 있다.
lookahead_time  —  s  —  속도 기반 Lookahead 사용 시 시간 지평. 최소·최대 거리와 함께 설정.

Graceful Controller 조정
min_lookahead / max_lookahead  —  m  —  가까운/먼 목표 선택 범위. 좁은 곳에서 너무 먼 목표는 추종을 어렵게 한다.
k_phi / k_delta  —  제어 이득  —  위치·방향 수렴 특성을 조정한다. 과도한 반응과 경로 오차를 함께 본다.
beta / 속도 제한  —  곡률 감속 / m/s  —  급커브에서 감속하는 정도와 최대 선속도·각속도를 맞춘다.

Rotation Shim 조정
angular_dist_threshold  —  rad  —  새 경로와 방향 차이가 크면 정렬 회전을 시작하는 기준.
rotate_to_heading_angular_vel  —  rad/s  —  정렬 회전 속도. 실제 회전·가속 한계를 넘지 않게 설정한다.
primary_controller — 클래스명 — 정렬 후 경로를 추종할 본 Controller. 래퍼와 본 제어기를 함께 설정한다.

Controller 선택 예제
넓은 실내·낮은 CPU 부담·경로 추종 중심: RPP를 비교한다.
동적 장애물과 미래 회피 궤적 비교: MPPI를 검토하고 처리 시간을 잰다.
DWB는 속도 샘플과 Critic을 관찰하며 비교한다. 같은 속도 한계로 실험한다.



Costmap과 주행 품질
Footprint · Inflation · Smoother
도착 판정 · 복구 · 실행 주기

Global · Local Costmap
Global  —  map 기준  —  목표까지 경로 계획. 저장 지도와 관측 장애물을 반영한다.
Local  —  odom / Rolling Window  —  로봇 주변 제어·충돌 평가. 센서 거리·예측 범위를 고려한다.
레이어 구성  —  Static·Obstacle·Voxel·Inflation  —  YAML에 정의만 해서는 활성화되지 않는다. plugins 목록을 확인한다.

Footprint와 해상도
robot_radius / footprint  —  m / 다각형 좌표  —  실제 로봇 외곽과 부착물을 반영한다. 통로를 지나게 하려고 축소하지 않는다.
resolution  —  m/cell  —  작게 하면 세밀하지만 셀 수와 계산·메모리 부담이 증가한다.
width / height  —  m  —  지역 지도 범위. 미래 궤적과 센서 가시 범위를 함께 고려한다.

Inflation 파라미터
inflation_radius  —  m  —  장애물 주변 비용을 퍼뜨리는 범위. 로봇 실제 반경과 구분한다.
cost_scaling_factor  —  감쇠 계수  —  같은 반경에서 크게 하면 비용이 더 빨리 감소한다.
조정 목적  —  벽과 거리 확보  —  중앙 통과 경향과 좁은 통로의 경로 가능성을 함께 관찰한다.

센서와 장애물 제거
obstacle_max_range  —  m  —  장애물 등록에 사용할 최대 센서 거리.
raytrace_max_range  —  m  —  레이저 광선을 따라 비어 있는 공간을 지우는 범위.
marking / clearing  —  bool  —  장애물 등록 / 해제. 유령 장애물은 시간·TF·센서 입력도 확인한다.

경로 평활화 선택지
Simple Smoother  —  위치 경로 평활화  —  격자 경로의 꺾임 완화. 운동학 제약 보장은 별도로 확인한다.
Savitzky–Golay  —  국소 다항 필터  —  경로의 작은 잡음을 완화. 필터 후 장애물·방향 전환 확인.
Constrained Smoother  —  제약 최적화  —  곡률·장애물·경로 품질을 고려. 계산 비용과 설정이 더 복잡하다.

Smoother 파라미터 선택
window_size / poly_order  —  창 크기 / 다항 차수  —  Savitzky–Golay의 국소 필터 범위. 창은 3 이상의 홀수. 지원 버전 확인.
w_smooth / w_cost  —  Constrained 가중치  —  매끄러움과 장애물 비용 사이 균형. 목표와 운동 제약도 함께 고려한다.
enforce_path_inversion  —  bool  —  지원 Smoother에서 전후진 전환점 보존. 설치 플러그인 항을 확인한다.

Smoother 적용 조건
플러그인을 설정해도 BT에서 SmoothPath를 호출하지 않으면 적용되지 않는다.
Hybrid·Lattice의 전후진 전환점과 최소 회전 반경을 보존해야 한다.
평활화 전후 경로가 장애물을 가로지르는지 Costmap에서 다시 확인한다.

도착과 진행 판정
xy_goal_tolerance  —  m  —  목표 위치 허용 오차. NavFn tolerance와 역할이 다르다.
yaw_goal_tolerance  —  rad  —  목표 방향 허용 오차. 지나치게 작으면 끝에서 계속 회전할 수 있다.
Progress Checker  -— 거리 + 시간  —  정해진 시간 내 진행 여부. 저속 실습에 맞는 판정 범위를 검토한다.

주행 명령 후처리
Velocity Smoother  —  속도·가감속 제한  —  명령 변화를 완화. Controller와 구동계의 한계를 일치시킨다.
Collision Monitor  —  센서 기반 감속·정지  —  추가 충돌 감시 계층. 센서 사각지대와 입력 지연을 확인한다.
Behavior Server  —  회전·후진·대기  —  실패 시 복구 동작. 막힌 곳에서 무조건 반복시키지 않는다.

주기와 계산량
controller_frequency  —  Hz  —  주기 안에 계산이 끝나야 한다. 높이는 것만으로 성능이 좋아지지 않는다.
update_frequency  —  Hz  —  Costmap 갱신. 센서 주기와 처리 부하를 함께 본다.
publish_frequency  —  Hz  —  Costmap 표시·전송 주기. 내부 갱신 주기와 구분한다.

파라미터 조정 순서
① 지도·TF·시간·센서·odom·AMCL을 먼저 확인한다.
② Footprint·Costmap·속도·가속 한계를 맞춘다.
③ Planner → Controller → 도착·진행 판정 순으로 조정하고 기록한다.

증상별 점검
벽에 너무 붙음  —  Footprint / Inflation  —  그다음 Planner 비용과 Controller 장애물 항을 본다.
코너에서 진동  —  위치·경로·후보 궤적  —  속도·회전 한계와 경로/목표 Critic 간 충돌을 점검한다.
명령은 있는데 정지  —  cmd_vel 타입·토픽·상태  —  TwistStamped 연결, Lifecycle active, 감시 정지 조건을 확인한다.



저장 지도 주행 실습
Gazebo Waffle · AMCL · Nav2
초기 위치 → 가까운 목표 → 알고리즘 비교

환경과 지도 확인
```
source /opt/ros/lyrical/setup.bash
export ROS_DOMAIN_ID=174
MAP_YAML="$HOME/slam_maps/maze_YYYYMMDD_HHMMSS.yaml"
ls "$MAP_YAML"
ros2 topic hz /clock
ros2 topic hz /scan
ros2 run tf2_ros tf2_echo odom base_footprint
```
YYYYMMDD_HHMMSS를 실제 저장 파일명으로 바꾼다.
Gazebo와 모든 터미널의 ROS_DOMAIN_ID를 일치시킨다.

Nav2 실행
```
ros2 launch nav2_bringup bringup_launch.py \
  map:="$MAP_YAML" \
  params_file:="$HOME/slam_maps/nav2_waffle.yaml" \
  use_sim_time:=true autostart:=true slam:=false \
  use_localization:=true use_composition:=false \
  use_keepout_zones:=false use_speed_zones:=false
```
먼저 README의 nav2_waffle.yaml 생성 절차를 완료한다.
Cartographer·cuVSLAM·키보드 텔레옵은 중지한 뒤 실행한다.

RViz와 초기 위치
```
ros2 launch nav2_bringup rviz_launch.py \
  use_sim_time:=true

ros2 lifecycle get /amcl
ros2 lifecycle get /controller_server
ros2 topic info /cmd_vel -v
```
2D Pose Estimate → 지도 벽과 스캔 정렬 확인
자유 공간의 가까운 목표에 Nav2 Goal을 지정한다.

실습용 속도 제한
MPPI  —  vx_max=0.1 / wz_max=0.2  —  m/s / rad/s. Waffle README의 시작값이며 최적값은 아니다.
Velocity Smoother  —  max_velocity=[0.1,0,0.2]  —  Controller 출력 제한과 맞춘다. 후진·가속 한계도 확인한다.
Stamped 명령  —  enable_stamped_cmd_vel=true  —  연결된 노드와 Gazebo 입력의 타입·토픽을 모두 일치시킨다.

알고리즘 교체 방법
작업용 YAML을 복사해 실험별 파일로 보관한다. 예: navfn_dwb.yaml, smac_mppi.yaml.
Planner·Controller의 plugin과 해당 파라미터 묶음을 함께 바꾼다.
교체 후 Nav2를 재시작하고 설치 클래스·노드 상태·토픽 연결을 확인한다.
